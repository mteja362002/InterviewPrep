# CONSTITUTION-005 — Assessment Engine

**Version:** 1.0  
**Status:** Active  
**Scope:** `backend/assessment/`  
**Authority:** Chief Software Architect  

---

## Purpose

The Assessment Engine is a **reusable, modular, deterministic evaluation platform**. It is the bridge between learning and evidence. It takes a learner's submitted attempt, evaluates it against a rubric, and produces structured, immutable evidence that downstream systems consume.

The Assessment Engine is the sole producer of `AssessmentEvidence`. It is the sole owner of the `assessments` MongoDB collection. It knows nothing about what happens to evidence after it is produced — it exposes, it does not apply.

---

## Responsibilities

### Assessment Engine Owns

- The `Assessment` aggregate root and its lifecycle
- Assessment question generation from the problem bank
- Rubric-based evaluation (deterministic, no AI)
- Structured feedback production
- Immutable `AssessmentEvidence` production
- Next-step recommendations (continue/revise/advance/reattempt)
- The `assessments` MongoDB collection
- The REST API (`assessment/api.py`)

### Assessment Engine Does NOT Own

- How evidence is used to update learner state (owned by Learner Intelligence `evidence_integration.py`)
- Mission generation or task composition (owned by Mission Engine)
- Problem selection strategy (owned by Problem Selector — Assessment Generator calls the selector)
- LLM-based question generation (Assessment questions come from the curated problem bank only)
- The `assessment_available` flag on `DailyMission` (owned by Mission Engine)

## Architectural Principles

### AE-001 — Evidence is Immutable

`AssessmentEvidence` MUST be `frozen=True` (Pydantic `ConfigDict(frozen=True)`). Once constructed, it MUST NEVER be modified. It is a permanent historical record.

### AE-002 — Evidence is Type-Agnostic

`AssessmentEvidence` MUST use only normalized scalar fields (0..1 or -1..1). It MUST NOT contain assessment-type-specific fields at the top level. Type-specific detail goes in the `metrics` dict. This ensures that Learner Intelligence, Analytics, and future consumers work identically regardless of assessment type.

### AE-003 — Evaluation is Deterministic

`evaluation_engine.evaluate(attempt, rubric, question)` MUST produce the same `Result` for the same inputs. No randomness. No AI. No external calls. Pure computation.

### AE-004 — The Engine Exposes, Never Applies

The Assessment Engine produces `AssessmentEvidence` and stops. It MUST NOT update `knowledge_nodes`, update mastery scores, schedule revisions, or trigger any learner state change. All application of evidence is the responsibility of `learner_intelligence/evidence_integration.py`.

### AE-005 — The Orchestrator is Thin

`assessment_engine.py` is a thin coordinator. It sequences the single-responsibility modules (generator → session → evaluation → feedback → evidence → recommendation) but contains no scoring logic, no rubric definitions, and no evidence transformation code. All business logic lives in the individual modules.

### AE-006 — Questions Reference, Not Duplicate

Assessment questions are generated by reference to `problem_bank` entries (via `problem_id`). The `Question` object stores the `problem_id` and surface metadata. It MUST NOT copy the full problem text or solution into the assessment doc. The problem bank is the single source of problem truth.

### AE-007 — Attempt Counting is Historical

The attempt number for a node is counted from historical `assessments` records for the same `(user_id, roadmap_node_id)`. It is never derived from a counter on the user document. This makes attempt history auditable and self-consistent.

### AE-008 — Session State Machine is Enforced

State transitions MUST follow the defined machine:

```
PENDING → STARTED → SUBMITTED → EVALUATED → COMPLETED
```

An invalid transition (e.g., SUBMITTED → STARTED) MUST be rejected. `assessment_session.py` is the single place that enforces transitions.

## Design Philosophy

The Assessment Engine exists because PrepOS needs a structured checkpoint between learning and advancing. A learner who has studied a node and solved Arena problems needs to prove understanding before advancing — otherwise mastery claims are unverified.

The key design decisions:

1. **Deterministic evaluation over AI evaluation:** AI-based evaluation is subjective and expensive. Rubric-based evaluation is reproducible, auditable, and instant. AI enrichment (feedback language) is a future add-on, not a prerequisite.

2. **Immutable evidence over mutable scores:** Changing a score retroactively corrupts the historical record. Immutable evidence lets us append new assessments and derive current state from the history.

3. **Type extensibility via enum + registry:** New assessment types (MCQ, Behavioral, System Design) add a new generator and register it. The evaluation framework, evidence schema, and API are unchanged.

4. **Disjoint problems for Arena and Assessment:** A learner who solved the representative problem in the Arena MUST see a different problem in the Assessment. Otherwise the Assessment measures "can you recall what you just saw" rather than "can you apply the pattern."

## Assessment Lifecycle

```
POST /api/assessment   (CreateAssessmentRequest)
           │
           ▼
    create_assessment()
    ├── default_difficulty(position) → difficulty
    ├── get_generator(assessment_type) → generator function
    ├── generator(roadmap_node_id, difficulty, target_company) → Question
    │       └── For coding: select_representative() with Arena exclusion
    ├── get_rubric(assessment_type) → Rubric
    └── Persist Assessment(PENDING) → assessments collection

POST /api/assessment/{id}/start
           │
           ▼
    start_assessment()
    └── session.start(a) → status: STARTED

POST /api/assessment/{id}/submit
           │
           ▼
    submit_assessment(req: SubmitAssessmentRequest)
    ├── Count prior attempts from assessments history
    ├── Build Attempt from req
    ├── session.submit(a, attempt) → status: SUBMITTED
    └── Persist

POST /api/assessment/{id}/evaluate
           │
           ▼
    evaluate_assessment()
    ├── evaluate(attempt, rubric, question) → Result
    ├── build_feedback(result, question) → Feedback
    ├── build_evidence(a, result, attempt, question) → AssessmentEvidence (FROZEN)
    ├── build_recommendation(evidence, feedback) → AssessmentRecommendation
    ├── session.mark_evaluated(a) + session.complete(a) → status: COMPLETED
    └── Persist Assessment with full Result + Evidence + Recommendation
```

## Rubric-Based Evaluation (Coding)

### Rubric Dimensions (Coding)

| Dimension Key | Weight | Measures |
|--------------|--------|---------|
| `correctness` | 0.40 | `passed_tests / total_tests` ratio |
| `time_complexity` | 0.25 | Claimed complexity vs. expected (optimal/suboptimal/unknown) |
| `edge_cases` | 0.20 | `edge_cases_passed / edge_cases_total` ratio |
| `code_quality` | 0.10 | Code present in submission |
| `explanation` | 0.05 | Explanation present in submission |

Weights MUST sum to 1.0 per rubric. New rubrics MUST follow this constraint.

### Verdict Thresholds

| Score | Verdict |
|-------|---------|
| ≥80 | CORRECT |
| ≥50 | PARTIALLY_CORRECT |
| <50 | INCORRECT |

### Confidence Delta Formula

```
confidence_delta = (proficiency - 0.5) * 0.4
```

Range: -1..1. Positive when proficiency > 0.5, negative when < 0.5.

## AssessmentEvidence Schema

```python
class AssessmentEvidence:
    schema_version: str         # "1.0" — bump on breaking schema changes
    assessment_id: str
    user_id: str
    assessment_type: str        # one of AssessmentType enum
    roadmap_node_id: Optional[str]
    mission_id: Optional[str]

    # Normalized scalars (0..1)
    accuracy: float             # correctness: passed_tests / total_tests
    proficiency: float          # weighted rubric score / 100
    completion_quality: float   # combined coverage + quality metric
    confidence_delta: float     # -1..1 — signed confidence suggestion

    difficulty_achieved: Optional[str]  # easy|medium|hard

    # Boolean signals
    weakness_confirmation: bool  # performing poorly on a previously weak node
    revision_trigger: bool       # performance warrants spaced-repetition re-scheduling
    repeated_mistakes: bool      # same node failed on multiple attempts

    # Extensibility (type-specific normalized metrics)
    metrics: dict[str, float]   # e.g., {"edge_case_coverage": 0.75}
    signals: dict[str, bool]    # mirrors boolean signals for uniform dict access
    tags: list[str]             # qualitative markers

    created_at: str             # ISO timestamp (set once, never changed)
```

**Schema evolution rules:**
- Adding new fields to `metrics` or `signals` does NOT require a `schema_version` bump
- Renaming or removing top-level fields REQUIRES a `schema_version` bump
- Consumers MUST check `schema_version` before reading evidence from the database

## Extension Points

### New Assessment Type

1. Add to `AssessmentType` enum in `schemas.py`
2. Implement `generate_<type>_assessment(roadmap_node_id, difficulty, target_company) → Question`
3. Register in `assessment_types.py` registry
4. Implement rubric in `rubrics.py` (dimensions must sum to 1.0)
5. Implement evaluation logic in `evaluation_engine.py` or submodule
6. Implement feedback logic in `feedback_engine.py`
7. `evidence.py` and `recommendations.py` require no changes (they are type-agnostic)

### New Rubric Dimension

Add to the rubric definition in `rubrics.py`. Adjust weights to sum to 1.0. Add computation logic in `evaluation_engine.py`. No schema changes.

### AI-Enhanced Feedback

A future phase may add AI-generated feedback text after deterministic evaluation. This MUST be additive: run `evaluate()` first (deterministic), then optionally enrich `Feedback.strengths/weaknesses` with AI-generated text. The `AssessmentEvidence` MUST remain deterministic — AI enrichment affects only the `Feedback` object.

## Performance Expectations

| Operation | Target |
|-----------|--------|
| `create_assessment()` | <100ms (1 DB read + 1 write) |
| `submit_assessment()` | <100ms (1 DB read + 1 write) |
| `evaluate_assessment()` | <50ms (pure computation + 1 DB write) |
| `list_for_user()` | <100ms (indexed query) |

Assessment evaluation MUST be synchronous. No background jobs for the evaluation pipeline.

---

## Invariants

1. `AssessmentEvidence` is frozen (`frozen=True`) and NEVER mutated after creation.
2. The `assessments` collection is write-only from outside the Assessment Engine. Only `assessment_history.py` writes to it.
3. Every `Assessment` document has exactly one `evidence` field (set after evaluation; `null` before).
4. Arena problems and Assessment problems are always disjoint (enforced by `split_arena_assessment()`).
5. `schema_version` is set at creation time and NEVER changes on an existing document.
6. State transitions follow PENDING → STARTED → SUBMITTED → EVALUATED → COMPLETED only.

---

## Anti-patterns

❌ Evaluation that calls an LLM to determine correctness  
❌ Assessment Engine updating `knowledge_nodes` directly  
❌ Assessment Engine reading from `daily_missions`  
❌ Mutable `AssessmentEvidence` (any code that modifies evidence after creation is a bug)  
❌ Rubric weights that don't sum to 1.0  
❌ Question objects that duplicate full problem content from the bank  
❌ Two separate modules both writing to the `assessments` collection  
❌ Bypassing `assessment_session.py` to set `status` directly  

---

## Future Evolution

- **AI-assisted evaluation:** After deterministic rubric scoring, an optional AI pass enriches the `Feedback` object with detailed code review comments. The `AssessmentEvidence` remains deterministic.
- **Behavioral assessments:** Add a `behavioral` generator that presents a behavioral question and accepts a text explanation. Evaluation rubric: completeness, STAR method adherence, specificity.
- **System design assessments:** Add a `system_design` generator tied to HLD roadmap nodes. Evaluation rubric: component coverage, scalability considerations, trade-off articulation.
- **Assessment analytics:** A future Analytics subsystem queries `assessments` with a read-only aggregate view. It MUST NOT write to `assessments`.
- **Reattempt limits:** Add a `max_attempts` field to `Assessment`. The session state machine enforces the limit. This is additive — existing assessments have no limit.
